Delivery is usually a step in a pipeline, not a website you visit. The API lets your own systems do it: create a transfer, stream the bytes, send it, and find out who collected it. Every account can use it: transfers, contacts and webhooks on the free plan, collections on a paid one.

## Ways in

- **From a terminal:** `npm install -g yungle-cli`, `yungle login`, then `yungle send ./dist`. [More](/cli)
- **From an AI assistant:** add `https://yungle.co/mcp` as a remote MCP server and sign in. No key. [More](/mcp)
- **From your code:** `npm install yungle-client`, `pip install yungle`, or any HTTP client against the [reference](/api-reference).
- **From CI:** the [GitHub Action](https://github.com/marketplace/actions/send-files-with-yungle) sends a build's output and hands the link to the next step.

The CLI, the MCP server and the TypeScript and Python SDKs are open source (MIT) on [GitHub](https://github.com/heindewilde/yungle-clients). Issues and pull requests are welcome there.

## Quickstart

Create a key in [Settings → API keys](https://yungle.co/dashboard/settings/api), then check it works:

```bash
curl https://yungle.co/api/v1/me \
  -H "Authorization: Bearer $YUNGLE_API_KEY"
```

Sending a file is three calls plus the upload itself — or one command with the CLI:

<CodeGroup>

```bash curl
# 1. Create the draft. Nothing is live and nobody is emailed yet.
curl -X POST https://yungle.co/api/v1/transfers \
  -H "Authorization: Bearer $YUNGLE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"files":[{"name":"final-cut.mov","size":8123456789}]}'

# → { "transfer": { "id": "01J…", "slug": "…" },
#     "tusEndpoint": "https://yungle.co/files",
#     "files": [ { "id": "01J…", "uploadToken": "…" } ] }

# 2. Stream the bytes to tusEndpoint (resumable — see Uploading files).

# 3. Send it.
curl -X POST https://yungle.co/api/v1/transfers/01J…/finalize \
  -H "Authorization: Bearer $YUNGLE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"recipients":["client@example.com"],"message":"Final cut attached."}'
```

```bash CLI
npm install -g yungle-cli
yungle send final-cut.mov --to client@example.com --message "Final cut attached."
```

</CodeGroup>

## How it is shaped

- **Base URL** is `https://yungle.co/api/v1`. Everything is JSON in and JSON out.
- **File bytes never go through this API.** Endpoints that accept files hand you a tus endpoint and a per-file token; you stream to that. It is resumable at part granularity, which is the point — a 100 GB upload should survive a dropped connection.
- **Creating and sending are separate calls.** A transfer is created as a draft, so bytes land before anyone is emailed a link.
- **Resources are addressed by id, never by slug.** A share slug is a capability — anyone holding it can download — so it is returned but never used as an address.

## Versioning

`/api/v1` is additive-only. New fields and new endpoints may appear; existing fields will not change meaning or disappear, and no new required request field will be added. A change that would break a client gets `/api/v2` instead, and v1 keeps working.

The machine-readable contract lives at [/api/v1/openapi.json](https://yungle.co/api/v1/openapi.json) — OpenAPI 3.1, generated from the same definitions the server validates with, so it cannot drift from the running code. It needs no key to read.

## What we promise, and what we don't

Yungle is small and self-hosted in the EU. There is **no SLA and no uptime guarantee**: it runs on a single server with no failover, so a hardware fault or a bad deploy means downtime rather than a graceful failover. It has happened, and it will happen again.

What you do get: your files are encrypted at rest, nothing is sent to a US cloud, and every byte is served from the EU under a real DPA. If your integration needs a contractual uptime guarantee, Yungle is not the right choice today — and we would rather you found that out here than during an incident.

Free usage is genuinely free: <code>{apiFreeUsage}</code> of uploads through the API each month, <code>{apiFreeCalls}</code> calls, and <code>{freeTransfer}</code> per transfer — no card, no trial clock. Beyond that it is <code>{apiPricePerGb}</code> per GB uploaded, paid from credit you top up in advance. It is priced apart from the plans, so it works the same on Free, Leaf and Tree.

Prepaid on purpose. Nothing is ever served that has not been paid for, which means no invoice can arrive for traffic you did not expect and a runaway script cannot spend money you have not already given us. When the balance runs out your next upload is refused rather than your recipient's download failing — the refusal lands on you, where you can see and fix it, never on someone waiting for a file. What your recipients download is never metered at all. The call limit is an abuse guard rather than a price: it sits far above what a working integration uses, because a limit that trips in normal use is a support ticket, not a safeguard.

<Note>
The vault and end-to-end encrypted transfers are not reachable from the API, and cannot be — their keys are derived in your browser and never sent to us. [What the API cannot do](/unsupported) explains where that boundary is.
</Note>
